# 錯誤日誌 - 埠位佔用導啟動失敗 (2026-03-12)

## 問題徵兆
前端回報 `ERR_CONNECTION_REFUSED` 錯誤。手動執行後端時，輸出顯示例外：
`ERROR: [Errno 10048] error while attempting to bind on address ('127.0.0.1', 8000): [winerror 10048] 一次只能用一個通訊端位址 (通訊協定/網路位址/連接埠)。`

## 根本原因
連接埠 **8000** 已被舊有的後端進程或殭屍進程佔用（PID: 2608）。這通常發生在先前的伺服器未正常關閉，或並行開啟了多個開發實例時，導致新啟動的 FastAPI 無法綁定埠位。

 -- 後端複雜度增加 (依賴項的影響)
早期的後端可能只是一個簡單的 FastAPI 框架。但我們最近加入了 yfinance、pandas 以及 llama-cpp-python (AI 引擎)。
這些庫（尤其是 yfinance）在運行時會開啟多個子線程 (Threads) 或網路連線池。
在 Windows 系統上，當 Electron 發送簡單的 kill()訊號時，有時候只殺掉了「主進程」，但那些負責處理網路數據或 AI 運算的「子進程/線程」卻沒有被連根拔起，變成了殭屍進程，繼續佔用著 8000 埠位。
 
 -- Windows 進程樹的處理機制
在之前的版本中，後端啟動方式比較直接。隨著功能增加，啟動腳本現在透過 Electron 的 spawn 調用 Windows 系統路徑下的 Python。

之前：如果進程結構單一，簡單的結束訊號就能關閉。
現在：Python 進程會開啟多個子層級。在 Windows 上，普通的kill()函數不具備遞歸性（它不會去殺掉孫子輩的進程）。這就是為什麼我現在必須改用 taskkill /T /F，其中 /T 就是代表「殺掉整個進程樹 (Tree)」。

 -- Socket 殘留 (TIME_WAIT 狀態)
因為我們增加了「投資研究」功能的即時同步（每隔幾秒抓一次資料），這意味著當您關閉軟體的那一刻，後端很可能正在進行網路通訊。

如果關閉時網路連線正好掛在那裡，Windows 的通訊端會進入一個叫 TIME_WAIT 的保護狀態，鎖定該埠位一段時間以確保數據完整。
以前通訊量小，碰撞機率低；現在通訊頻繁，碰撞機率就飆升了。

## 解決路徑
1. **定位佔用者**: 透過命令 `netstat -ano | findstr :8000` 找出佔用該埠位的進程 ID。
2. **強制結束進程**: 執行 `taskkill /F /PID 2608` 強制釋放連接埠。
3. **驗證重啟**: 重新啟動後端伺服器，確認能順利看到 `Application startup complete` 的訊息。

## 預防措施
1. 在開發環境中關閉編輯器或終端機前，請確保先透過 `Ctrl+C` 正常中止後端服務。
2. 未來若再次發生，可執行偵查命令確認佔用狀況，而非盲目重複啟動。

為了徹底解決此問題，已於 `electron/main.cjs` 實作以下自動化邏輯：
1. **強化關閉邏輯**: 在 `app.on('before-quit')` 與 `window-all-closed` 事件中使用 `taskkill /F /T` 確保結束整個 Python 進程樹。
